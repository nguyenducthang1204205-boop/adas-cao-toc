# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Desktop ADAS app + Android app (graduation thesis): real-time following-distance warning on highways. YOLOv11 detects vehicles, IPM converts each vehicle's ground-contact point to road-plane metres, and speed-dependent thresholds trigger colour and sound alerts. An AI assistant (Claude) tunes the threshold parameters from natural-language driving conditions. UI text, comments and user-facing strings are in **Vietnamese**; keep new ones Vietnamese.

## Architecture

Packages follow the thesis architecture diagram (PI 2.2): `adas/stream` (Video Stream) → `adas/detection` (YOLOv11) → `adas/distance` (IPM distance: ipm, autocalib, lane, ego_speed, kalman, estimator) → `adas/alert` (thresholds, engine = AlertManager, violations) → `gui/`. Plus `adas/assistant` (offline.py rules, prompt.py, service.py = SafetyAssistant; the package `__init__` re-exports them), `adas/storage/database.py`, `adas/config.py`, `adas/paths.py`, `adas/formatting.py` (`vn`, `vn_num`, `vn_factor`). Core packages have docstring-only `__init__` files (no re-exports, to avoid import cycles such as alert.violations → pipeline → alert.engine); import modules by full path, e.g. `from adas.distance.ipm import GroundPlaneMapper`. All imports are absolute.

`adas/` has no Qt dependency at all. `gui/` is PySide6: `app.py` (QApplication setup, single instance; `main.py` only parses args and calls `gui.app.run`), `main_window.py`, `worker.py`, `dialogs/` (calibration, history, settings, sources), `widgets/` (common, stage, panels, tabs; the package re-exports everything), `rendering/` (qt.py = fonts/colours/icons/`bgr_to_qimage`; overlay.py = `render_overlay`, `render_bev`, `lane_edges`; package re-exports), `theme.py`, `styles.py`.

**Paths** live only in `adas/paths.py`: `APP_DIR` is the project root from source, or the folder of `ADAS.exe` when frozen (`sys.frozen`); `DB_PATH`, `SNAPSHOT_DIR`, `FONT_DIR`, `UI_ASSETS_DIR` (= `assets/ui`, formerly `gui/assets`) derive from it. `tools/build_exe.py` copies `models/` and `assets/` next to the exe. This machine's Smart App Control blocks running the unsigned exe (same policy that blocks `.venv`), so the frozen app can only be checked by simulating `sys.frozen` in the system Python.

Per-frame flow (`adas/pipeline.py::ADASPipeline.process`):
`VehicleDetector.detect` (YOLO + ByteTrack via `model.track(persist=True)`) every N frames, `TemplateTracker.track` on the frames in between
→ `DistanceEstimator.estimate`: IPM on bbox bottom-centre, far fallback, per-track Kalman filter (distance, closing speed), TTC
→ `compute_thresholds(speed, policy)` + `classify_risk` (`adas/alert/thresholds.py`), where `speed` is the measured ego speed (`EgoSpeedEstimator`) or `cfg.speed_kmh`
→ `AlertManager.update` (hysteresis: escalate once the new level has lasted `escalate_seconds` (default 0.1 s) over ≥ 2 frames, de-escalate after a hold time; pygame beeps). It is time-based, not frame-count-based, so a phone that drops to 10 Hz warns as early as one at 30 Hz; `AlertHysteresis` in the Android app (`core/Pipeline.kt`) is the same rule; `smoke_test.test_alert` checks the Python side.
Before distance estimation, `EgoLaneDetector.update` (`adas/distance/lane.py`) finds the ego lane from lane markings when `cfg.alert.auto_lane` is on. The lead vehicle is the nearest one inside that lane, or with `|lateral| ≤ lane_half_width` when no lane is confirmed. When `only_ego_lane` is set, other vehicles get risk `"info"`.

Key design points that span files:
- **IPM maps pixels straight to metres.** In `adas/distance/ipm.py`, `GroundPlaneMapper` builds H from 4 image points (stored as 0..1 ratios in config) to the rectangle `(±W/2, d0)…(±W/2, d0+L)` in metres. Y is the distance from the ego bumper and X is the lateral offset. Points above the horizon (homogeneous sign flip) and points beyond `max_range_m` return NaN, which triggers the Pinhole fallback. The same H drives the BEV warp (`bev_matrix @ H`) and the road-zone overlay (`ground_to_image`).
- **Pose calibration (default, 3-step wizard)** (`adas/distance/camera_model.py`, `gui/dialogs/calibration_wizard.py`; Android `core/CameraModel.kt`, `ui/calibration/CalibrationWizard.kt`). `CalibrationConfig.pose: CameraPose` holds height, bumper offset, `focal_w` (f / frame width), the vanishing point `vp_x/vp_y` (ratios; used instead of angles so changing f doesn't move the horizon) and roll. When `pose.active`, `calib_from_pose` projects a ground rectangle through the pose to produce the usual 4 `image_points`, so IPM, DB and the Kotlin port are unchanged. The wizard: vehicle preset or tape-measured height → horizon from `estimate_vanishing_point` (desktop) / gravity sensor + Camera2 focal (`service/CameraIntrinsics.kt`, Android) → done. The 4-point dialog is "Căn chỉnh nâng cao". DB methods `pose` / `online` (schema v4 rebuilt the table for the CHECK).
  - **A source without its own calibration row never inherits the previous source's calibration** (`MainWindow._activate_source` resets the geometry with `generic_calibration`, keeping lane corridor / range settings). A different camera's horizon put the ego-speed strip (Y 5–26 m) above the real horizon of `seoul_night_expressway_720p_10min.mp4` → ~1 km/h and a wrong lane. Instead `ProcessingWorker(auto_init=True)` runs `camera_model.AutoInitializer`: one `estimate_vanishing_point` per 15-frame window, accepted only when 5 consecutive windows agree (MAD ≤ 2 % h / 3 % w; single windows jump to rows 520–550 on that video), median VP + car preset + FOV focal → `calibration_initialized` → saved as a `pose` row; online calibration refines it. No violations are written while it is pending; it gives up after 90 windows. `smoke_test.test_auto_init` covers it.
- **Online calibration** (`adas/distance/online_calib.py`, `AppConfig.auto_calib`; Android `core/OnlineCalib.kt` + `core/LaneLines.kt`, a light image-space lane finder because `lane.py` isn't ported). Input per frame is a `LaneObservation` (2 image points per ego-lane line). The VP *row* uses all samples (horizontal curvature only shifts the VP sideways; a shifted camera also makes straight lines look curved in the BEV), the *column* only straight-road samples. After `SAMPLES_NEEDED` (150 desktop / 90 Android at 15 Hz) over ≥ 5 s: pose calibrations get the median VP, height scaled to a 3.75 m lane unless measured, and (desktop, once, `focal_source == "fov"`) focal fitted so video speed matches `ref_speed_kmh`; the result is returned in `CalibStatus.new_calib` and the GUI/ViewModel applies + saves it. A later run (every Start makes a new calibrator) whose re-measured pose matches an already `refined` one within `SAME_DEG` 0.25° / `SAME_REL` 2 % only reports a check, so no duplicate rows. **GPS scale** (phone, no user input): every frame with GPS ≥ 30 km/h that has been steady (±2 km/h over 2 s, so GPS lag doesn't matter) and a video speed (`EgoSpeed.kt`, a port of `ego_speed.py` on the two `LaneLines` lines) adds an estimate of the true metres between two image rows fixed at the first sample (`scale of current calib × GPS / video`, independent of later calibration changes; skipped 2 s after a change while the video speed re-smooths). After ≥ 200 estimates over ≥ 20 s with MAD ≤ 6 %, the median sets the focal (`focal_source = "gps"`): new calib if off by ≥ 1.5 % (otherwise "khớp GPS"), refit only if ≥ 3 % and ≥ 30 s later; a later height rescale keeps f·h. Drift clears the estimates. On `videoplayback.mp4` with the overlay as GPS (1 Hz, rounded, 1 or 2 s lag), starting from the default FOV (−10 km/h): fitted at 24 s, then +0,2 km/h bias / 1,2 MAE, as good as the hand-tuned #18. The Python `OnlineCalibrator.update(..., gps_kmh)` has the same logic (desktop passes None: no GPS). **Desktop video (no GPS): typed speed while the video plays.** The wizard no longer asks for a speed (it sets `ref_speed_kmh = 0`; the old one-shot path in `_finish` only serves old calibrations). While the calibrator wants a scale (`CalibStatus.ask_speed`: no GPS, pose active, `focal_source` not `speed`/`gps`, nothing pending) and the source is a video file, `MainWindow`'s calib bar shows "Tốc độ trên video: [..] km/h Dùng"; the video time at the *first keystroke* (= when the number was read, `_video_t()` = frame/fps, the worker's time base) goes with the value through `ProcessingWorker.speed_reference` → `OnlineCalibrator.add_reference(t, kmh)`. The calibrator keeps `scale / video speed` for the last 15 s and, 2 s after `t`, turns the ±2 s window (≥ 15 samples) into a true-scale estimate (same fixed rows as GPS) → focal fit with `focal_source = "speed"` (in `_finish` if still collecting, else `_ref_check`); no dashed lines then → "Chưa đo được…" and the input comes back. On `videoplayback.mp4` from the default FOV: typing at 2 s → −0,5 km/h (MAE 1,3), at 10 s → −1,9, at 35 s → +4,0 (the video speed itself reads ~4 % low there, also with #18), so it is only as good as the moment. 4-point calibrations are only checked (lane width) and warned on drift. Drift = recent VP median off by > 1° (row) / 1.5° (column) → re-collect. `make_mobile_fixtures.py` writes `calib_python.json` + `lane_python.json`/`lane_frames.bin.gz`; `CalibTest.kt` replays them step by step.
- **Auto-calibration** (`adas/distance/autocalib.py`, "Tự động căn chỉnh" button in the advanced 4-point dialog) uses the flat-road model `Y = K/(v−v0)`. The vanishing point comes from Hough+RANSAC, camera height from the per-frame ego-lane pixel width (3.75 m lane), and `K = f·h_c` from the shift of the dashed-line pattern between frames at the user-entered ego speed. It emits a `CalibrationConfig` whose trapezoid is symmetric about the VP column, so X=0 is the heading axis. Distances are from the front bumper (`bumper_offset_m`, default 2 m).
- **Ego-lane detection** (`adas/distance/lane.py`, toggle `AlertConfig.auto_lane`, default on). It warps grey to a metric BEV with the calibrated H (X ±6 m, Y 4–36 m), applies a horizontal top-hat (paint narrower than 0.6 m), and masks YOLO boxes. It then runs sliding windows along the previous fit (or a column-histogram re-search) and fits `X = c0 + c1·Y + c2·Y²` per line, with curvature clamped to R ≥ 300 m.
  - Acquisition needs **both** lines with a plausible width (2.2–5.2 m) on 3 consecutive frames, and the lane must contain the ego axis (±0.4 m). Until then it returns `None` (single images, night city streets). After that, a missing side is inferred from the smoothed width. A centre jump of more than half a lane (a lane change) snaps instead of smoothing. The lane is lost after 20 frames with no lines.
  - `FrameResult.lane` drives `in_ego_lane` (`LaneEstimate.contains`), the overlay zones, the BEV corridor and a HUD line, all through `gui.rendering.lane_edges`. `None` falls back to `±lane_half_width_m`.
  - The measured width is only as right as the calibration's lateral scale. A known 3.75 m lane reading ~4.7 m means the 4 manual points are off.
- **Ego speed from video** (`adas/distance/ego_speed.py`, `AppConfig.auto_speed`, default on). It samples brightness along each *found* lane line in metres (Y 5–26 m, ±0.25 m lateral max − median, via `cv2.remap` on the original image, which is sharper than the BEV) and keeps only dashed profiles. The current profile is matched to the one ~0.08–0.4 s earlier by normalized correlation with parabolic sub-sample refinement, then `v = shift/Δt` and the median over 1 s, smoothed by an EMA (τ = 1 s, after a 1 s warm-up that follows the median directly) and output with a 1 km/h deadband. Single samples scatter ±8 km/h; without the EMA the shown number changed ~8×/s. Against the GPS overlay of `videoplayback.mp4` (calibration #18) the MAE is ~1.3 km/h.
  - Once a value exists, the shift search is limited to 0.6–1.4× the prediction, so it can't alias onto the next dash.
  - A whole-frame BEV phase correlation does **not** work here: at 640×360, Y 4–24 m spans only ~60 image rows, and the solid line and blur pin the peak at 0. Never average a solid-line "measurement" in, because it pulls the result towards 0.
  - The pipeline runs the lane detector when `auto_lane` **or** `auto_speed` is on, and only uses the lane for `in_ego_lane` when `auto_lane` is on. `FrameResult.speed_kmh` / `speed_measured` drive the thresholds, the HUD, `violations.speed_kmh` and the stats (`speed_auto`). It falls back to `cfg.speed_kmh` when there is no measurement (or images, where `track=False`).
  - GUI: in `SpeedPanel`, clicking a step or the assistant returning a `speed_kmh` turns auto off. `MainWindow._on_frame` ignores queued frames from a stopped worker (`sender()` check), so late signals can't restore stale values.
- **Sparse detection, dense tracking** (`adas/detection/tracking.py`, `ModelConfig.detect_every`: 0 = auto, 1 = YOLO every frame). YOLO runs every N frames. On the other frames each track is re-measured by NCC template matching on a grey image shrunk to ≤ 640 px wide:
  - The anchor template is a ≤16×16 bilinear grid taken in the box at the last YOLO frame.
  - Search: coarse position scan (step 2 px) at the current scale, then ±1 px × scales 0.97/1/1.03, then parabolic sub-pixel refinement. NCC < 0.6 marks the box `source="coast"` (the Kalman filter predicts only).
  - A track that YOLO misses in 2 consecutive passes is dropped. A 1 s grace period produced "ghost" lead cars for up to a second.
  - Auto N = `ceil(yolo_ms / (0.5·frame_dt))`, capped at 4, with the GPU warm-up run excluded. On a GPU that gives N = 1; on CPU (~40 ms YOLO), N = 3.
  - `_tracker_ready` forces YOLO on the first frame and after switching from N = 1.
  - On `videoplayback.mp4` with N = 3: the detection stage drops from 10.0 to 5.3 ms/frame and tracking costs ~1 ms. Lead distance is within 0.63 m (median, cars < 60 m) of YOLO-every-frame, and the warning level agrees 98 % of frames.
  - Synthetic test: box error ~0.5 px.
  - Level agreement is only roughly reproducible, because `AlertManager` hold times use wall-clock time.
- **Kalman filter** (`adas/distance/kalman.py`, used by `DistanceEstimator` in `adas/distance/estimator.py`). It uses a constant-*acceleration* state `[d, ḋ, d̈]` with jerk noise σj = 10 m/s³ and measurement σ = max(0.3 m, 4 %·d). The 4 % is the residual of per-track IPM distances around a smooth 1 s fit on `videoplayback.mp4`.
  - Closing speed and TTC are reported only once `rate_std < 2 m/s` (~0.6 s after a track appears). A 5σ gate rejects single-frame outliers, and 3 outliers in a row re-initialise the filter.
  - Simulated lead braking at 6 m/s² against the old EMA + 1 s regression: detection lag 415 vs 608 ms, closing-speed error while braking 1.4 vs 3.5 m/s, and the same steady-state noise.
  - A constant-velocity model was tried and rejected: 1.1 s lag.
  - `smoke_test.test_kalman` / `test_tracker` cover both.
- **Far/invalid IPM points** (above the horizon or beyond `max_range_m`) get method `"Xa"`, a distance of at least `max_range_m`, and risk `"info"`. This keeps ordering consistent with IPM-measured vehicles. The Pinhole estimate uses `mapper.focal_px`, which is derived from H, not the vfov guess.
- **Threshold formula** (`adas/alert/thresholds.py`): `base = legal_table(v)` if V ≥ 60 km/h, else `v·time_gap_s` (2 s rule, an estimate because the law leaves V < 60 to the driver). Then `safe = max(base, min_distance) × weather_factor` and `danger = max(min_distance, safe × danger_ratio)`.
  - The legal table uses exact boundaries: 60 → 35 m, (60, 80] → 55 m, (80, 100] → 70 m, (100, 120] → 100 m. Boundary tests are in smoke_test.
  - Per-band customization (required by the thesis outline): `SafetyPolicy.band_gaps_m` holds the user's dry-road warning distance per legal band, set in Settings → "Ngưỡng cảnh báo" (with `time_gap_s` for V < 60). `band_gap_m` floors each band at the legal value, so `base` is never below the law. `condition_policy`, the Claude path and the condition reset keep the user's bands and `time_gap_s`. The Android app has the same bands (`SafetyPolicy.bandGapsM`, `bandGapM`, `conditionPolicy(base =)`, persisted in `AppSettings`, edited in Settings → "Ngưỡng cảnh báo" with the same rows, limits and live preview); `CoreTest.thresholdsMatchPython` checks it against Python fixtures.
  - `threshold_basis(thr, policy)` / Kotlin `thresholdBasis` produce the one-line explanation shown under "GIỮ TỐI THIỂU" on both platforms (weather factor on a second line). The fixtures compare the exact strings, so change both together.
  - Adverse weather is applied **once**, via `weather_factor`, from `ROAD_CONDITIONS` presets (factor ≈ 0.7/μ) times `MODIFIERS`, capped at 3.0. Don't also raise `time_gap_s` for weather, which would double-count.
  - `visibility_m > 0` produces `recommended_speed_kmh` (stopping distance ≤ visibility).
  - The Claude system prompt table is generated from `ROAD_CONDITIONS`, so edit the presets, not the prompt.
- **The AI assistant is outside the frame loop.** `adas.assistant.SafetyAssistant.ask` (service.py) returns a new `SafetyPolicy`, which is applied to config, and the pipeline reads `cfg.policy` / `cfg.speed_kmh` on every frame.
  - Claude call: `client.beta.messages.create` with `output_config.format` json_schema (`RESPONSE_SCHEMA`) and server-side refusal fallback (`betas=["server-side-fallback-2026-07-01"], fallbacks="default"`, only for models in `FALLBACK_MODELS`), effort `low` (omitted for Haiku, which rejects it). Default model `claude-haiku-4-5` (cheapest; the Claude API has no free model). The choices are `config.ASSISTANT_MODELS`, and `AppConfig.load` resets a saved model not in that list to the default.
  - **Offline is the default** (`AssistantConfig.use_cloud = False`) so a packaged app needs no network or paid key. Claude is opt-in, and any exception falls back to `offline_advice`.
  - `offline_advice` uses Vietnamese keyword regexes and also accepts text typed without diacritics. Each pattern entry has multi-word phrases (matched whole-word on both accented and `_fold`ed text) plus single words that are matched only when the user typed diacritics, because folding makes words collide (mù/mưa, mệt/mét, tối/tôi, bão/báo). Test new phrases for these collisions.
  - The Android `core/Assistant.kt` (`OfflineAssistant.advise`) is a 1:1 port of `offline_advice` and must give byte-identical replies. So reply numbers use `_r()` (= `int(v + 0.5)`, Kotlin `Double.r()` = `Math.round`) and `vn_num`, never `:.0f` (banker's rounding) or `:.2f`. Kotlin uses `java.text.Normalizer` for fold/NFC; `\b` must be Unicode-aware like Python, which Android regex always is, but Android *throws* on the `Pattern.UNICODE_CHARACTER_CLASS` flag (that crashed the app on the first assistant question while JVM unit tests passed), so `Assistant.kt` passes the flag only where it compiles (unit-test JVM); `fixed()` formats with `BigDecimal(v).setScale(n, HALF_EVEN)` to match Python f-strings. When you change patterns or texts, edit both files and regenerate `assistant_python.json` (`AssistantTest` checks 342 cases).
  - `clamp_policy` enforces `LIMITS`; keep the schema, the system prompt's stated ranges and `LIMITS` in sync.
- **Database** (`adas/storage/database.py`, SQLite `data/adas.db`, `python tools/init_db.py` to create/inspect). Each call opens a short-lived connection (WAL), so the worker thread and GUI can both use `Database()`.
  - `AppConfig.load()` / `cfg.save(reason)` read and write the `system_config` table (one row per `section.key`, JSON values). A history row is added to `config_history` only when the snapshot differs. On first run, `config/settings.json` is imported and renamed to `settings.imported.json`.
  - The worker opens a `monitoring_sessions` row per run. `adas/alert/violations.py::ViolationRecorder` writes one `violations` row per **episode** (open when the stable level is warning/danger with a lead; update on escalation; close when safe or the lead track changes). DB writes happen only at those points. Snapshots go to `data/snapshots/session_<id>/`, stored as paths relative to the app dir.
  - `camera_calibrations` holds one row per calibration: K, H, R and the params. The latest row per source is active. The matrices come from `GroundPlaneMapper.model` (`ipm.py::_decompose`: Zhang decomposition of H⁻¹ with the principal point at the frame centre). Schema v3 migrated the old `video_sources.calibration_json` into this table and dropped the column. Design doc with the architecture and ERD: `docs/THIET_KE_HE_THONG.md`.
  - The per-stage timings (`FrameResult.timings_ms`: stream / detection / ipm / alert / gui) are shown in the status bar (`gui.widgets.perf_text`).
  - `video_sources` holds the registered sources. `uri` is unique and normalized by `sources.normalize_source`, so file paths are absolute and use backslashes. `MainWindow.start()` → `_activate_source` registers the source and loads its latest calibration (`params_json`). Accepting the calibration dialog inserts a new calibration row, recording whether it was manual or auto. Schema migrations (v1→v2: `source_id` on sessions; v2→v3: calibration table) run in `init_schema`.
  - Tests that run the GUI or worker should point `Database.__init__.__defaults__` and `adas.violations.SNAPSHOT_DIR` at temp locations, so they don't pollute the user's DB.
- **Shared mutable config.** `AppConfig` (nested dataclasses in `adas/config.py`, persisted in the DB) is shared by reference between the GUI thread and `gui/worker.py::ProcessingWorker` (QThread).
  - Always mutate it with `update_inplace(dst, src)`. **Never reassign** `cfg.policy`, `cfg.alert`, etc., because `AlertManager` and the estimator hold references to them.
  - After a calibration or class change, call `worker.calibration_changed()` / `classes_changed()`. The worker applies these at the next frame.
- **Main window layout** (`gui/main_window.py`, widgets in `gui/widgets/`: `stage.py` = WelcomePanel/VideoStage/PlayBar, `panels.py` = StatusCard/SpeedPanel/ConditionPanel, `tabs.py` = ChatPanel/EventLog, `common.py` = helpers):
  - Layout: a header (`setMenuWidget`) with the source menu (open video/camera/image, recent sources from `list_sources`, manager), a single Start/Stop button, Record, Sound, Calibrate, History and Settings. Below it, a notice bar appears when the active source has no calibration row. The body is a splitter: `VideoStage` + `PlayBar` on the left, and a scrollable right column (`StatusCard`, `SpeedPanel`, `ConditionPanel`, then tabs Trợ lý AI / Vi phạm).
  - Shortcuts live on window-level `QAction`s (`addAction`), and header/playbar buttons wrap them with `setDefaultAction`.
  - `VideoStage` shows `WelcomePanel` (3 steps: source, calibration, start) until the first frame. It places the BEV beside the video when there is room, otherwise as a bottom-right inset, and shows it only once a frame exists.
  - The condition chips call `chat.submit(text)`, the same path as typing, so the assistant stays the only way to change the policy from the main window. After any policy change call `_policy_changed()`, which refreshes both cards.
  - Fitting at 1536×864 (1080p at 125 % scaling): `QScrollArea` sizes its widget by height-for-width, i.e. *preferred* heights. The bottom tabs are `_FillTabs`, which report their minimum size and `hasHeightForWidth() = False`, so the column fits without scrolling. Measure `minimumSizeHint()` before adding to the right column. The weather chips use an `Ignored` horizontal size policy so they share the width.
- **Design system "Night Drive", shared with mobile.** Tokens are `gui/theme.py` (`C`, `LEVEL_STYLE`, Material icon codepoints `ICONS`, `CONDITION_ICONS`); decimal-comma formatting `vn()` / `vn_factor()` / `vn_num()` is `adas/formatting.py`; `gui/app.py` sets the default `QLocale` to Vietnamese so spin boxes show "2,5". They mirror the Android `ui/theme/Theme.kt`; change both together.
  - Fonts (Be Vietnam Pro + Material Icons, same as the mobile app) live in `assets/fonts/` and are registered by `gui.rendering.ensure_fonts()`: `gui/app.py` calls it, and `font()` / `icon_font()` call it lazily (headless included).
  - **No emoji anywhere in the UI.** Use `gui.rendering.icon(name, color, size)` for QIcons, `gui.widgets.set_icon(button, ...)` (adds the icon-text gap), and `gui.widgets.icon_html(...)` inside rich text. Be Vietnam Pro lacks `● ✓ ⚠ ↺ ▾ μ → ↔`, so these glyphs must not appear in strings.
  - `render_overlay` (`gui/rendering/overlay.py`) matches the Android `OverlayRenderer` (`ui/drive/Overlay.kt`):
    - a neutral corridor, with only the gap to the lead tinted in its risk colour;
    - threshold marks (danger label left, warning right) are drawn only in front of the lead;
    - chevrons, corner-bracket boxes, and pill labels with collision avoidance, where the lead label wins;
    - a banner pill and an edge glow.
  - `info=True` adds a glass info box. It is used only for recordings and violation snapshots, because those lack the right-hand column.
  - `assets/ui/app_icon.png` is the mobile launcher icon (rounded).
- **Styling** (`gui/styles.py`): colour tokens come from `gui/theme.py` via `C` (also used by QPainter widgets), and widgets are styled by `objectName` (`card`, `primary`, `chip`, `speedStep`, `startButton[running]`, `notice`, `step[done]`…). After `setProperty` on a property used in a selector, call `gui.widgets.repolish(w)`. Dialog OK buttons get `setObjectName("primary")`; don't use `:default`, which also matches auto-default Cancel buttons. Asset `url()`s must be quoted because the app path contains a space ("Đồ án").
- **Rendering uses QPainter on QImage**, not `cv2.putText`, because OpenCV cannot draw Vietnamese diacritics. It runs in the worker thread. Use `bgr_to_qimage` / `qimage_to_bgr` (Format_BGR888, stride-aware) to convert; recording writes `qimage_to_bgr(overlay)`. Headless use needs a `QGuiApplication` for fonts (see smoke_test).
- **Sources** (`adas/stream/sources.py`):
  - `VideoFileSource` paces playback to wall-clock and drops frames when behind (`realtime_playback`); call `restart_clock()` after a pause.
  - `CameraSource` uses a grabber thread and always returns the newest frame.
  - Image files are read with `np.fromfile` + `cv2.imdecode` because the project path contains non-ASCII characters ("Đồ án") and `cv2.imread` fails on it. Use the same trick for any new image I/O.
- **Worker lifecycle** (`gui/main_window.py`): `stop()` is synchronous (it waits, then calls `_on_finished(w)`). The finished handler only clears `self.worker` if it matches, so late signals from an old thread are ignored.
- **Weights:** `models/best.pt` (custom), falling back to `models/yolo11n.pt` (COCO), falling back to an Ultralytics auto-download. Device `auto` means CUDA `"0"` if available. Don't pass `half=` to predict/track: the installed Ultralytics has deprecated it.

## Mobile app (`mobile/android`)

Native Android app: Kotlin + Jetpack Compose, one Android Studio project in `mobile/android` (open that folder in Studio and press Run). User guide and model results: `mobile/README.md`. The former Flutter app is archived untouched in `mobile/flutter_legacy/` (no longer maintained; its own docs and paths are stale).

```bash
cd mobile/android
powershell -ExecutionPolicy Bypass -File build_apk.ps1 [-Test] [-Install]   # release APK -> mobile/android/dist/ADAS_CaoToc.apk
```

- **Non-ASCII path ("Đồ án").** `java.exe` decodes argv / `@argfiles` with the ANSI code page, which has no "Đ": `gradlew(.bat)` can't find `gradle-wrapper.jar`, and forked unit-test JVMs get `ClassNotFoundException`. Fixes in place: the root `build.gradle.kts` moves every `buildDirectory` to `%LOCALAPPDATA%\adas_android_build\<module>` when the project path is non-ASCII (APKs land in `...\app\outputs\apk\...`); `build_apk.ps1` copies the wrapper to `%LOCALAPPDATA%\adas_gradle_wrapper` and runs it with the project as working directory. `gradle.properties` sets `android.overridePathCheck=true`. `local.properties` needs `sdk.dir=C\:/Users/...` (forward slashes; single backslashes are eaten by Properties parsing). Without the script, call the cached Gradle directly: `~/.gradle/wrapper/dists/gradle-9.3.1-all/*/gradle-9.3.1/bin/gradle`, with `JAVA_HOME` = Android Studio's `jbr`.
- **Stack.** AGP 9.1 with built-in Kotlin (don't apply `org.jetbrains.kotlin.android`; it is only on the root classpath with `apply false` to pin Kotlin 2.4.0), Compose BOM 2026.06.01, material-icons-extended 1.7.8 (it has no `Foggy`, so fog uses `Cloud`; use `Icons.AutoMirrored.*` for VolumeUp/ReceiptLong/ArrowBack/Send), CameraX 1.6.2, LiteRT 1.4.0 (`org.tensorflow.lite.Interpreter`, `GpuDelegate` + `CompatibilityList`). minSdk 26, compile/target 36. Versions live in `gradle/libs.versions.toml`. `.tflite` assets are `noCompress` (memory-mapped).
- **Layers** (package `vn.adas.caotoc`):
  - `core/`: pure Kotlin, no Android imports except `org.json` (unit tests add the real `org.json:json`). 1:1 ports of the Python algorithms: `Ipm.kt` + `Geometry.kt`, `Distance.kt`, `Kalman.kt`, `TemplateTracker.kt`, `Safety.kt` (thresholds, `conditionPolicy`, `thresholdBasis`), `Pipeline.kt` (`AlertHysteresis`, `AdasPipeline`), `Violations.kt`, `Assistant.kt`; plus `Detection.kt` (YOLO decode + NMS, letterbox), `IouTracker.kt` (only when dense tracking is off), `Roi.kt` (wide/narrow YOLO crops), `Governor.kt`, `VnText.kt`. Config classes are immutable `data class`es.
  - `detector/`: `YoloDetector.create` benchmarks GPU FP16 (when `CompatibilityList` supports it) against CPU XNNPACK INT8 with 1/2/4 threads and keeps the fastest; `Preprocessor` (YUV420 → letterboxed RGB float NHWC in a direct ByteBuffer, crop-while-resize, integer ×1024 BT.601); `Gray.fromPlane` (Y plane, f×f box average down to ≤ 640 px); `FramePacket` (copied YUV planes for the YOLO thread).
  - `engine/FrameEngine.kt`: `process()` runs on the CameraX analysis thread (`STRATEGY_KEEP_ONLY_LATEST` replaces the old busy/ack logic). It sends a frame to a single-thread YOLO executor when YOLO is free and `yoloIntervalS` allows; the result lands in an `AtomicReference` and is merged on the next frame via `TemplateTracker.refresh(detT = capture time)`. With dense tracking off, the pending YOLO result goes through `pipeline.process` on the next frame. The YUV packet buffer is reused only after the YOLO thread has returned it. `close()` waits for an in-flight YOLO run so the detector can be closed right after.
  - `data/`: `AppSettings` (immutable, same JSON keys as the old Flutter app; `SettingsStore.update { it.copy(...) }` → SharedPreferences + StateFlow) and `ViolationLog` (last 500 episodes, written only on open/escalate/close, no snapshots). `AdasApp` (the Application) owns both.
  - `service/`: `AlertPlayer` (SoundPool beeps by level + vi-VN TextToSpeech on escalation, 5 s voice cooldown), `GpsSpeed` (LocationManager GPS, drops fixes with speed accuracy > 3 m/s, light EMA, stale after 3 s), `DeviceInfo` (thermal status/headroom, device info for benchmark reports).
  - `ui/`: `drive/DriveViewModel.kt` (activity-scoped; engine lifecycle, GPS, alerts, recorder, chat, self-test notice, HUD throttling: overlay `live` on every result, clusters `hud` ≤ 10 Hz unless level or lead presence changes), `DriveScreen.kt` (permissions, CameraX preview, sheets), `Hud.kt` (pure presentation fed by `HudState`; `FitHeight` scales the clusters down on short screens), `Overlay.kt` (`CoverTransform` = FILL_CENTER mapping image → screen, so strokes and text are drawn in dp directly), `CameraPreview.kt`, `Sheets.kt` (conditions sheet, "Trợ lý AI | Vi phạm" sheet); `calibration/`, `settings/`, `benchmark/`, `welcome/`, `theme/Theme.kt` (Night Drive tokens), `components/`. Navigation is a simple screen enum in `MainActivity`; the welcome/disclaimer gate is `AppSettings.disclaimerAccepted`.
- **Governor, ROI, assistant, violations, bands** behave exactly as on desktop and in the old mobile app: levels Cao / Trung bình / Thấp = tracking every frame / 15 Hz / 10 Hz with 4 / 3 / 2 detailed tracks; capability < 50 ms / ≤ 120 ms YOLO, > 300 ms = "máy yếu"; thermal caps; risk-adaptive YOLO pacing; narrow far crop every 3rd YOLO run when calm. Ego speed comes from GPS (manual fallback). The full lane detector is not ported (fixed `±lane_half_width_m` corridor); `LaneLines.kt` + `EgoSpeed.kt` only feed the online calibration, and the shown speed stays GPS (the tech readout adds "Theo vạch kẻ N km/h · GPS M km/h").
- **Tests.** `app/src/test/.../CoreTest.kt` + `AssistantTest.kt` + `CalibTest.kt` (23 tests) read `src/test/resources/fixtures/*`, produced by `python tools/make_mobile_fixtures.py` (it writes there and reads the model from `app/src/main/assets/models`). `tools/export_mobile.py` also writes models straight into the Android assets.
- **Emulator** (`Pixel_6_Pro` AVD; start headless with `-no-window -gpu swiftshader_indirect -camera-back virtualscene`; debug APK `%LOCALAPPDATA%\adas_android_build\app\outputs\apk\debug\app-debug.apk`, `adb install -r -g`): welcome → HUD → camera → YOLO → IPM → warning → overlay → assistant sheet verified. It has no usable GPU delegate and YOLO takes ~4.7 s on CPU, so the whole emulator gets CPU-starved (System UI / IME ANRs, delayed taps). Don't trust interaction timing there.
- **Car head unit + USB dashcam** (`service/UsbCamera.kt`, `org.uvccamera:lib` 0.0.13 = libuvc/libusb, Apache 2.0, ARM-only `.so` with 4 KB page alignment). `AppSettings.cameraSource` is `auto` (default: USB when a UVC device is attached, else the phone camera), `phone` or `usb`. `ui/drive/CameraView.kt` picks `CameraPreview` (CameraX; falls back to any camera the system lists when there is no back camera) or a `TextureView` fed by the UVC camera. NV21 frames go through `engine/Nv21Frame.kt` into the same `FrameInput` / `FramePacket` path (V plane = offset w·h, U = +1, pixel stride 2; `CoreTest.nv21FrameMatchesI420`).
  - The camera is opened per activity (`MainActivity.onStart/onStop`) and streams only while a preview surface exists. The `TextureView` returns `false` from `onSurfaceTextureDestroyed`, so `UsbCamera` stops the preview before releasing the surface.
  - The manifest makes `android.hardware.camera` optional, the activity is `singleTask`, and it has a `USB_DEVICE_ATTACHED` filter (`res/xml/usb_camera.xml`: class 239/2 or 14). Choosing "always open" once means the app launches with USB permission whenever the car powers the camera. The CAMERA permission is still needed (Android 9+).
  - In the calibration wizard, with a USB camera the gravity sensor is skipped (it sits in the head unit, not the camera). The focal comes from the dashcam's diagonal FOV printed on the box (f = half-diagonal / half-angle, equidistant fisheye, default 140°) as a starting point; the GPS scale fit refines it, and a previous `gps`/`speed` focal is kept.

## Accuracy caveats (from README)

- Distances are only meaningful after IPM calibration for the actual camera: "Căn chỉnh camera" dialog, 4 points on lane edges, VN expressway lane = 3.75 m. Defaults are a guess.
- IPM assumes a flat road, and error grows sharply beyond about 80–100 m.
- Ego speed is measured from video when `auto_speed` is on (`adas/distance/ego_speed.py`). Otherwise it is manual (speed-step buttons or AI chat). There is no GPS/OBD input. The measured speed is only as right as the calibration's depth scale: on `videoplayback.mp4` the saved manual calibration reads ~55 km/h against a GPS overlay of ~74 km/h, while auto-calibration gives −6 %.
